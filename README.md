📄 コーディング規約 ＆ セルフチェックリスト
この規約は、プログラムを「動かす」だけでなく、チームの資産として「誰でも読める・直せる」状態に保つための最低限のルールです。 提出（プルリクエスト）前に、必ず以下のチェックリストを確認してください。

1. 命名規則(クラス・変数)
名前は「情報の要約」です。中身を推測できない名前はバグの温床になります。

 英単語のみを使用しているか
日本語（漢字・かな・カタカナ）や、ローマ字（namaeなど）は使用禁止。
 変数・メソッド名は「ローワーキャメルケース」か
小文字で始め、単語の区切りを大文字にする。（例：employeeName, getSalary()）
 クラス名は「アッパーキャメルケース」か
大文字で始め、単語の区切りを大文字にする。（例：EmployeeService）
 メソッド名の規則は動詞＋名詞か
名詞で表現するものに対し何をするかをメソッド名では明らかにすること。（例：getEmployeeId）
 定数は「スネークケース（大文字）」か
すべて大文字、単語をアンダースコアで繋ぐ。（例：MAX_RETRY_COUNT）
 意味のある名前か
a, s, data などの抽象的な名前は禁止。targetUser, errorMessage など、役割を明示する。
 boolean型は「肯定形」か
isMember など。isNotMember（二重否定の原因）は避ける。
2. コードの見た目
清潔感のあるコードは、ロジカルな思考の現れです。

 自動整形（Ctrl + Shift + F）を実行したか
インデント（字下げ）がズレていないか確認。
 適切な空行が入っているか
論理的な処理の塊ごとに1行空け、文字が密集しすぎていないか。
 Eclipseの警告（黄色い波線）をゼロにしたか
未使用の変数、Scannerの閉じ忘れなど。意図的な例外（@SuppressWarnings）を除き、警告はすべて解消する。
3. ロジック・品質
「なんとなく動く」ではなく、「意図して動かす」コードを目指してください。

 マジックナンバーを排除しているか
数字や文字列を直接書かず、必ず定数（static final）として宣言して使用しているか。
 単一責任の原則を守っているか
1つのメソッドで「計算」と「表示」を同時に行うなど、２つの動作を持っていないか。
メソッドの長さが「画面1枚（最大80行程度）」に収まっているか。
それ以上になる場合は、メソッドを細かく分割するなど検討する。
 アクセス修飾子は適切か
最初は private を検討し、必要最小限の範囲だけで公開（カプセル化）しているか。
 グローバル変数を乱用していないか
メンバ変数は「クラス全体の状態」を保持するものに限定し、メソッド内の計算用変数はローカル変数として定義しているか。
4. コメント
コメントは「コードの補足」ではなく、「意図の表明」です。

 「Why（なぜ）」が書かれているか
i++; // iを増やす といった「見ればわかること（How）」は書かない。
「なぜこの計算が必要なのか」「なぜこの条件で分岐させるのか」という意図を記述する。
 コードそのものが読みやすいか
コメントを大量に書く前に、名前や構造を工夫して「読めばわかるコード」にできないか検討したか。
