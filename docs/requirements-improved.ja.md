論理的な穴・曖昧箇所を修正した改訂版である。原文の構成を踏襲しつつ、以下の変更点サマリに
該当する箇所を修正・追記した。

## 0. スコープの境界

### 0-1. 対象チャネルの明確化

東京都公式サイトに掲載されている「都政に対する提言・意見・要望等の受付と活用について」の図によれば、
都民の声は次の6チャネルから受け付けられている。

- 電話 / 来訪 / メールフォーム・LINE / FAX / 手紙 / 意見箱

このうち性質が全く異なる（音声・対面・紙・テキスト）ため、それぞれ別のインジェスト技術
（音声認識、AI-OCR、対面受付システム等）が必要になり、システムとしては当然別物になる。

**本プロトタイプがデジタル化・自動仕分けの対象とするのは、この中の「メールフォーム・LINE」に相当する
テキスト入力チャネル（＝本システムの `/submit` フォーム）のみ**である。電話（Speech-to-Text連携）、
紙・FAX（AI-OCR連携）、来訪・意見箱は本プロトタイプの対象外とする（当初案のOut-of-Scope欄を踏襲）。

### 0-2. 既存の二系統受付構造との関係

同図から、実際の都の運用では「都民の声総合窓口（政策企画局戦略広報部）」と「各局等都民の声窓口
（各局等広聴担当）」が別々に声を受け付けており（総合窓口: 年間約3.3〜3.4万件、各局直接: 年間約7.3〜7.7万件）、
両者が「連携」して件数等を報告し合い、共通の月報・年報公表サイクルに乗せている。

これは本要件定義書の「ガバナンス通知チェーン」構想（現場出先機関の特定時に上位局・総合窓口へ
同時共有する階層連動型ワークフロー）の実務的な裏付けとなる、既存の実在プロセスである。

### 0-3. 本システムの位置づけ（既存フローの一部自動化）

**本システムは既存のデータフロー（受付→処理→活用→公表、総合窓口⇄各局の連携）を置き換えるものではない。**
変わるのは「処理」工程内の一部分だけである——これまで職員が意見内容を読んで関係局等を判断していた
（前掲図の「○提言・意見・要望等の内容から関係局等を判断」）手作業を、システム（現時点ではルールベースの
判定エンジン、将来的にLLMへ拡張可能）が支援・肩代わりする、という位置づけである。
「新しい並行パイプラインを作る」のではなく「既存の判断工程に自動化を挿入する」ものとして設計している。

## 1. データ調査・フィジビリティ検証

### 1-1. 利用オープンデータセット定義（変更なし）

原文どおり、以下5データセットを使用する。

| No | データセット名 | 提供元 | 役割 |
| :-- | :-- | :-- | :-- |
| 1 | 都政への提言・意見・要望等の受付・対応状況 | 政策企画局 | RAG類似事例検索 |
| 2 | 東京都組織規程・事務分掌データ | 総務局 | ハルシネーション抑制のグラウンディング |
| 3 | 東京都 都有施設一覧データ | 財務局/各局 | 施設名からの都管轄判定 |
| 4 | 東京都管理道路（都道）路線・境界データ | 建設局 | 道路名からの都管轄判定 |
| 5 | 東京都 区市町村一覧・コードデータ | 総務局 | 管轄外案件の案内文生成 |

プロトタイプでは上記5種を模したモックデータ（`src/main/resources/data/*.json`）を用いている。

### 1-2. データクレンジング・前処理設計（変更なし、運用プロセスを追記）

原文の前処理設計（A〜D）は妥当であるため踏襲する。ただし以下を追記する。

**組織改編マッピングの継続運用（B節への追記）**: 「福祉保健局」→「福祉局」「保健医療局」のような
旧組織名の置換マッピングは、一度作成して終わりにできるものではない。東京都の組織改編は毎年度発生しうるため、
以下の運用プロセスを提言する。

1. 総務局が公開する事務分掌データの更新を定期的（月次目安）に差分検知する。
2. 差分が検知された場合、影響を受ける過去データのマッピングテーブルを更新するまでの間、
   該当局・部への自動ルーティングのconfidenceに一時的なペナルティ（例: -0.15）を適用し、
   古い組織名に基づく誤ルーティングのリスクを下げる。
3. マッピングテーブルの更新履歴をバージョン管理し、いつの時点のマッピングでルーティングされたかを
   追跡できるようにする。

### 1-3. 検証用データセット（Ground Truth）の作成と判定・通知設計

原文の受付・判定ポリシー（すべて正式受付、区市町村案件は案内文生成、不適切キューは隔離監査）は
妥当であるため踏襲する。50件のベンチマーク設計についても構成（5カテゴリ）は妥当だが、
サンプルサイズの限界については4-1で後述する。

**出力スキーマの穴（重要な修正）**: 原文の `classification_type` は
`TOKYO_METROPOLITAN | JURISDICTION_OTHER | UNKNOWN` の3値のみで、`is_inappropriate` とは
別フィールドとして定義されていた。この設計だと「不適切と判定された案件のルーティング表現」が
スキーマ上明確でない（`classification_type` を何にすべきかの規定が無い）という穴がある。

本プロトタイプでは暫定対応として、`is_inappropriate=true` の場合に
`routing.primary_bureau = "INAPPROPRIATE_QUEUE"` というセンチネル値を設定し、
管理画面側は `is_inappropriate` を最優先のフィルタ条件として扱う設計とした。
**v2改訂案**として、`classification_type` に `"INAPPROPRIATE"` を正式な値として追加し、
`is_inappropriate` フィールド自体を廃止して一本化することを推奨する。

**複数局複合案件のスキーマ不足（重要な修正）**: 原文のテストケース3
（「駅前の違法駐輪対策と都営バスの増便要望」＝建設局＋交通局）のように、1件の意見に複数の担当局が
またがるケースが明記されているにもかかわらず、出力スキーマの `routing` は
`primary_bureau`/`primary_division`/`primary_section`/`action_owner` という単一主体を前提とした構造になっている。

本プロトタイプでは、`governance_notification_tree` を使って両局の通知チェーンを並列に含める形で
擬似的に表現した（政策企画局を調整役として追加）。**v2改訂案**として、`routing` に
`secondary_routings: RoutingEntry[]` のような複数局対応の配列フィールドを追加することを推奨する。

**confidence閾値の意味の具体化（重要な修正）**: 原文は「confidence_score >= {{CONFIDENCE_THRESHOLD_HIGH}}
の場合のみ自動割り振りを確定」「それ未満は無理に推測せずUNKNOWNとする」とのみ記載しており、
LOW閾値（0.70）が具体的に何をゲートするのかが未定義だった。本プロトタイプで採用した解釈は以下の通り:

- `score >= HIGH(0.85)`: 自動ルーティングを確定する（`classification_type = TOKYO_METROPOLITAN`）。
- `LOW(0.70) <= score < HIGH`: `classification_type` は `UNKNOWN` に倒すが、
  管理画面のトリアージ一覧には「推定局ヒント」を補助表示する（都民向けの確定ルーティングには使わない、
  あくまで職員の手動トリアージを助けるための非スキーマ項目）。
- `score < LOW`: ヒントも出さず、単純にUNKNOWNとして総合窓口の手動トリアージに委ねる。

### 1-4. プロンプト＆RAGの変数化・厳格推論仕様（変更なし）

変数定義・システムプロンプト・出力スキーマは原文の設計を踏襲する（1で述べたスキーマ修正を反映済み）。
本プロトタイプでは `PromptTemplate.java` にドキュメントとして保持しており、実LLM（Gemini API等を想定）への
差し替え時にそのまま利用できる。

## 2. プロダクト要件・機能定義

### 2-1. MVPスコープ定義

原文のMVPスコープ図・In-Scope/Out-of-Scopeは概ね妥当。F-A05を以下のとおり拡充した。

### 2-2. 機能要件一覧（F-A05を拡充）

**F-A05: オープンデータ自動パブリッシュ機能（拡充）**

原文は「月報・年報用の集計データおよびAPIエンドポイントを生成」とダウンロード導線のみを想定していたが、
「行政がそのまま眺めて使える可視化ページ」であるべきという指摘を受け、以下へ拡充した。

- 匿名化集計を局別件数・分類タイプ別内訳・月別推移・不適切検知率・平均confidenceとしてページ上に
  グラフ表示する（棒グラフ・円グラフ・折れ線グラフ）。
- ダウンロード形式をCSV・JSONに加えてExcel（.xlsx）にも対応する。
- グラフ描画は外部JSライブラリ・CDNを一切使わず、サーバ側でSVGを直接生成する
  （後述のセキュリティ設計におけるCSP方針 `default-src 'self'` と整合させるため）。

これにより、KPI「オープンデータ循環度＝入力5種＋新規生成1種＝計6データセット」の
"新規生成データセット"を、実際にダウンロード・閲覧可能な成果物として担保する。

### 2-3. 定量的評価指標（KPI）の再検証（重要な修正）

原文のKPIは目標値のみが示され、根拠・測定方法が不明確だった。以下のとおり再定義する。

**ルーティング正解率（目標85%以上）**

- 「正解」の定義を明確化する必要がある: 局のみの一致か、部・課まで一致した場合のみを正解とするか。
  本改訂では「主担当局が一致すること」を正解の最低基準とし、部・課・現場出先機関まで一致した場合は
  「完全正解」として別集計することを推奨する。
- n=50のベンチマークは統計的に心もとない。二項分布の信頼区間（95%）で見ると、85%の観測正解率でも
  実際の正解率は概ね ±9〜14ポイント程度の幅を持ちうる。**カテゴリごと20件以上・合計150件以上への
  拡張を推奨する。**

**ハルシネーション（誤判定）率（目標0%）**

- 「LLMの振る舞いとして0%を達成する」という主張は、生成AIの性質上、原理的に保証しづらい。
- 本プロトタイプで採用した設計は、**アーキテクチャレベルでの保証**である: 担当組織名は必ず
  事務分掌データセットに実在する値のみを許可し、実在しない部署名が出力された場合は
  ポストホックなバリデータで検出し、機械的にUNKNOWNへフォールバックさせる。
  これにより「LLMがハルシネーションを起こさない」のではなく「ハルシネーションが起きても
  それを検出して握りつぶし、UNKNOWNに倒す」という設計で0%を実現する。この違いを審査資料でも
  明確に説明することを推奨する。

**仕分け業務削減時間（推計70%）**

- 算出根拠（時間あたり単価×件数×削減率などの計算式）が示されておらず、現状は説得力に欠ける。
- 測定計画を以下のとおり提案する: (1) 導入前のベースラインとして、職員の意見仕分け・連絡に要する
  平均対応時間をタイムスタディで計測する。(2) 導入後、実際の対応時間ログ（システムの `createdAt`〜
  `ASSIGNED`到達時刻の差分等）を継続的に収集する。(3) 一定期間（例: 3ヶ月）運用後に両者を比較し、
  実測に基づく削減率を報告する。

### 2-4. セキュリティ設計（新設）

ユーザー要望により、全システム（都民向けポータル・行政向け管理画面・オープンデータ公表ページ）共通で
以下のセキュリティ対策を実装した。ハッカソン規模のプロトタイプとして現実的に実装できる範囲であり、
本格的な運用には追加対応が必要な点も明記する。

| 対策 | 実装内容 |
| :-- | :-- |
| XSS対策 | 都民入力（意見本文・件名）を表示する全箇所でJSTL `<c:out>` によるエスケープを徹底し、生HTML挿入・スクリプトレット直書きを禁止 |
| CSRF対策 | 状態変更を伴う全POSTにセッション単位のワンタイムトークンを要求し、不一致時は400で拒否 |
| 管理画面の認証・認可 | `/admin/*` 全体をセッションベース認証でガード。セッションCookieは `HttpOnly`・`SameSite=Strict` |
| セキュリティヘッダ | `Content-Security-Policy: default-src 'self'`、`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、管理画面は `Cache-Control: no-store` |
| 入力検証 | 件名・本文の必須／文字数上限をサーバ側で必ず再検証 |
| CSV/Excelインジェクション対策 | セル値の先頭が `= + - @` の場合はエスケープし、数式実行を防止 |
| PIIの取り扱い | オープンデータ出力に生の意見本文・氏名・連絡先を一切含めない。サーバログにも出力しない |
| 簡易レート制限 | 都民投稿エンドポイントにIPアドレス単位の簡易トークンバケットを実装 |
| 監査ログ | 管理操作（アサイン・不適切復元・通知ステータス変更・エクスポート実行）を記録 |

**本プロトタイプでは対応していない事項**（本番運用移行時に必須）: 本格的なペネトレーションテスト、
WAF、TLS終端（デモはHTTP前提）、多要素認証、実際のSSO/LDAP連携、依存ライブラリの継続的脆弱性
スキャン運用、パスワードハッシュのBCrypt/Argon2等への置き換え（現状はSHA-256+ソルトの簡易実装）。

### 2-5. PIIマスキングの具体化（重要な修正）

原文の「個人情報を自動マスキングした上でリアルタイム集計」という記述だけでは、実装方針が不明確だった。
以下のとおり具体化する。

1. **集計データにはそもそも生テキストを含めない**: 意見本文・件名は公開用オープンデータへは一切出力せず、
   局別・分類タイプ別・月別の**件数集計のみ**を公開する（本プロトタイプの `AggregatedStats` はこの方針を徹底）。
2. **少数セルの抑制（k-匿名性）**: 特定の局×分類タイプの組み合わせで件数が極端に少ない
   （例: 5件未満）場合、個人が特定されうるリスクがあるため、当該セルは「5件未満」のように
   丸めて公表する。
3. **案内文・回答文ドラフトに含まれうる住所・電話番号等**は、正規表現ベースのマスキングパターン
   （電話番号: `0\d{1,4}-\d{1,4}-\d{4}` 等、メールアドレス: 標準的なメール正規表現）を適用してから
   公開用途に転用する。

## 3. 実装状況（初版からの追加実装）と非対応事項

初版のプロトタイプ提出後、以下を追加実装した。

- **本番想定のデータベース**: H2（純Java・ネイティブ依存なし）へ移行。JDBC URL差し替えでPostgreSQL等の本番RDBMSにも対応できる設計。
- **都民向け／行政向けシステムの完全分離**: citizen-portal（都民向け、既定ポート8080）とadmin-portal（行政向け、既定ポート8081）を別Tomcatインスタンス・別Mavenモジュールとして完全に独立させ、データベースのみを共有する構成に再編。
- **実LLM（Gemini API）連携**: `GEMINI_API_KEY`環境変数が設定されていれば実際にGemini APIで判定し、未設定・失敗時はルールベースのモックへ自動フォールバック。ハルシネーション防止のポストホック検証（存在しない部署名の機械的却下）を実LLM経路でも実施。
- **実際の通知配信**: メール（Angus Mail）・Slack（Incoming Webhook）への配信を実装。未設定時は安全にスキップ。
- **電話・FAX・窓口来訪・手紙・意見箱の統一代筆入力ページ**: `/admin/manual-intake`。都民本人によるオンライン投稿と同じ判定エンジンで処理される。
- **全30局の職員アカウント＋RBAC**: 事務分掌データに登場する都の全30局それぞれが独立ログインアカウントを持ち、政策企画局（総合窓口）は全案件横断閲覧、他局は自局担当案件のみ閲覧・回答文入力ができるアクセス制御を実装。
- **都民向け投稿フォームの実フォーム準拠**: 実際の都民の声総合窓口メールフォームの項目構成に合わせて全面改訂。連絡先情報は分類エンジンへ渡さず、オープンデータ出力にも含めない。
- **アクセシビリティ**: スキップリンク、フォーカス可視化、テーブル見出しscope、SVGグラフのrole/aria-label等。正式なWCAG監査は未実施。
- **LGWAN本番閉域網相当のアクセス制限（ベストエフォート）**: 実際のLGWAN接続はこの環境では再現できないため、IPアドレス／CIDRによるアクセス制限フィルタで近似。

以下は依然として未実装であり、本番化にあたっては別途検討が必要。

- 多要素認証・SSO/LDAP連携（現状はデモ用共通パスワード）
